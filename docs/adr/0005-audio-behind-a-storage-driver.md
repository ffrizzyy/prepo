# ADR 0005: Audio bytes live behind a storage driver, on disk

- Status: Accepted. Recorded 21 October 2026.
- Supersedes: none.

## Context

The specification puts recordings in a private Cloudflare R2 bucket and gives
the browser short-lived presigned URLs. There is no R2 account behind this
repository. The properties that matter are not "R2": bytes are private, a client
never chooses a key, authorization is checked before a byte is served, and range
requests work for the player.

## Decision

A `StorageDriver` interface with a local-filesystem implementation.

- `put`, `read`, `size`, `readRange`, `open` (a handle for streaming a range) and
  `remove`. A bucket driver implements the same interface; nothing above it
  changes.
- Keys are generated by the server as `<workspaceId>/<assetId><extension>`. The
  local driver resolves every key and refuses one that escapes the root, so a
  key cannot become `../`.
- The root is `AUDIO_STORAGE_DIR`, defaulting to `<cwd>/.storage/audio`. Bytes
  are never served by a static file handler: playback goes through a route
  handler that reads the session, resolves the asset inside the caller's
  workspace, and only then opens a range. "Not yours" and "does not exist"
  answer identically.
- Uploads are capped at 25 MB, 3 hours and 4 MB per chunk; the file type is
  sniffed from the bytes (a renamed file is not trusted by its extension); the
  recorded SHA-256 is metadata, not a re-check on every read.
- Audio retention defaults to 30 days after transcription, with choices of
  immediately, 7, 30, 90 days or keep forever; `db:retention` is the sweep, and
  abandoned uploads and never-transcribed recordings are reclaimed after 90
  days.

## Consequences

- Privacy is real but local: files sit on the machine that runs the app, with
  filesystem permissions as the outer boundary. There is no object-store ACL,
  no lifecycle rule, and no off-machine copy. A stolen disk steals the audio.
- A single node owns the bytes. Scaling the web app across machines without
  shared storage would serve 404s from the wrong instance. A bucket driver is
  the fix, and it is a constructor change.
- Backup must include two things: the database directory and `.storage`. The
  restore drill copies both and verifies the recording bytes are at their keys
  in the restored copy, which is why the drill is not a database-only drill.
- There are no presigned URLs, so the "presigned-URL issuer" row in the IDOR
  checklist has nothing to test. Authorization is per request instead.
- Deleting a recording is a database decision first and a file removal second;
  a crash between them leaves an orphan file, which the retention sweep is the
  place to reclaim.

## Alternatives considered

- **An S3-compatible service (MinIO) run locally.** Rejected: another service to
  start, and it would not make the demo more honest than the local driver.
- **Store bytes in the database.** Rejected: it inflates every backup and makes
  range reads a database operation.
- **Serve files from `public/`.** Rejected outright: that is unauthenticated by
  construction.
